# 让写作类 Skill「越用越强」的反馈闭环（Warp 自我改进法落地）

> 2026-08-29 分析 Claude 博文《How Warp builds self-improving agents on Claude》后，为用户 Cowrite 平台设计的"写作反馈 → 自动改进 humanizer-zh"方案骨架。用户已确认：反馈源=Cowrite 人肉改稿 diff；触发=改稿后说「收录反馈」+ 手动；审核=每周汇总批审；MVP=先 humanizer-zh 单点。**尚未开发，方案待确认后实施。**

## 一、核心判据（为什么不能纯自迭代）
写作**没有标准答案**（不像代码能过测试）。用户已实证写作类自我进化 Skill 会越改越糟——根因是**没有统一基准 + 盲目吸纳**。因此必须走 Warp 一文结论：**人负责高维标注/评论/反馈，Agent 负责执行并根据人类反馈改进 Skill**，且加护栏——人在环审核、有限反馈源、先建可测基准，**不做全自动自迭代**。

## 二、六块机制（表格式）
| 环节 | 做法 |
|---|---|
| ① 反馈源 | Cowrite 人肉改稿 diff（信号最准、零额外成本） |
| ② 触发 | 改稿后说一句「收录反馈」 |
| ③ 提取 | 扫描这次改稿 → 提炼"humanizer-zh 缺了哪条规则/哪条太激进"→ 生成 patch 草案（改了什么+为什么+证据） |
| ④ 审核 | 每周汇总批审，用户在飞书点选确认，Agent 不直接改 |
| ⑤ 落地 | patch 到 humanizer-zh SKILL.md（先备份，可回滚） |
| ⑥ 基准验证 | 用可测 AI 味指标前后对比，确认真改善才采纳 |

## 三、Warp 6 条最佳实践（可直接复用）
1. 写**原则**，不写死规则（"找重复代码"优于详尽命名规则）
2. 解释**为什么**（让 Agent 推理、举一反三）
3. 让反馈**无摩擦**（在人们原本工作的地方收集，自动发生）
4. 保持**精简 + 渐进披露**（引用资源/脚本，不塞爆上下文）
5. 反馈**质量>数量**（但数量也有帮助）
6. **改进 Skill 可复用**（元层，可跨用例移植）

## 四、如果反馈是错的（护栏）
- 永远不让 Agent 盲目接受反馈，给足够上下文做合理性检查
- 限制**谁**有权影响技能更新（不是所有人意见同等重要）
- 始终保留**人在循环中**审核改动
- 有标准答案的领域（代码过测试/部署成功）→ 建**验证基准**让 Agent 自己跑；无标准答案的领域（代码风格/文档质量）→ 靠**领域专家**判断，不开放给所有人

## 五、本次侦察得到的关键前提（决定方案成立与否）
1. **Cowrite 不存页面历史**（详见 SKILL.md 主文「页面无历史 + 成稿快照」节）——改稿 diff 无法自动采集。解法：用户选"说一句「收录反馈」"触发，靠对话上下文提供改前/改后文本，**零 Cowrite 改造**。
2. **humanizer-zh 无客观基准**——纯 SKILL.md（18 类规则 + 自评 1-10×5 维），无配套词表/脚本，自评而非可测基线。需先建可测指标（AI 味词汇命中率/破折号/三段式/连接词/句子方差）作为前后对比标尺。

## 六、待确认点（用户拍板后开发）
- 「收录反馈」触发词与格式：建议 `收录反馈：<页面标题>，改稿理由：<一句话>`
- AI 味指标脚本位置：建议 humanizer-zh 目录 `scripts/ai_taste_check.py`

## 七、可量化 AI 味指标（建基准时参考）
从 SKILL.md 规则里可直接脚本化的：AI 高频词命中（此外/至关重要/强调/格局/织锦…）、破折号 `—` 计数、`不仅…而且…`/`不仅仅是…而是…` 否定排比、`从 X 到 Y` 虚假范围、三段式列举、句子长度方差、`作为/标志着/体现了` 夸大象征。这些可做前后对比，是"反馈有没真改善"的客观标尺。
