# 峰峰人物 × 任意动作与场景融合规范

## 定位

本规范解决的不是“人物如何操作机器”这一单一问题，而是所有人物与场景结合问题：人物是否真的在做动作、是否受到环境约束、动作是否改变对象、人物和场景是否像同一张图。

用户认可图 `assets/calibration/approved-character-machine-integration.jpg` 只用于校准“真实接触、统一空间、连续因果链”；不得把纸片、摇柄、机器或左右构图固化成模板。

## 通用交互模型

每个含峰峰的镜头都必须先写 `interaction_mode` 和 `interaction_contract`。

交互契约包含：

1. `actor`：谁在行动，默认 Feng。
2. `intent`：为什么做这个动作。
3. `action`：可见动词，如推、拉、写、接、打开、坐下。
4. `target`：动作作用于什么对象、人物或环境。
5. `contact_points`：哪些身体部位与哪些对象部位接触。
6. `motion_or_force`：运动/受力方向、旋转轴或视线方向。
7. `body_response`：重心、手臂、躯干、步态、表情如何响应动作。
8. `object_response`：目标对象发生什么可见变化。
9. `occlusion`：接触处谁遮挡谁，证明两者处于同一空间。
10. `result_state`：动作完成后画面必须出现的结果。

通用因果链：

`意图 → 身体动作 → 接触/视线关系 → 对象响应 → 结果状态`

如果动作和结果之间没有可见因果关系，人物就是装饰。

## 交互模式与资产路由

### `none`

没有人物，或人物完全不参与本场。

### `gaze-gesture`

观察、思考、惊讶、指向、说明、总结等不需要精确接触的动作。

- 可使用透明人物素材叠加 HTML/SVG。
- 必须有明确视线或手势目标，不能看向空处。
- 指向只代表“引导注意”，不能冒充操作。

### `surface-contact`

触摸、点击、按压、书写、绘画、滑动、翻页等与平面或界面接触的动作。

- 接触点简单且对象仍由代码层驱动时，可使用分层合成，但必须先用 Hero Frame 验证指尖/笔尖接触。
- 接触复杂、透视明显或手部遮挡关键时，改为整帧生成。

### `force-contact`

推、拉、握、转、举、放、搬、投、插、拔、连接、拆卸等有受力和对象位移的动作。

- 默认整帧生成。
- 必须显示身体受力、接触遮挡和对象响应。

### `body-support`

坐、靠、扶、趴、跪、攀爬、跨越等身体重量由环境承托的动作。

- 默认整帧生成。
- 必须显示臀/脚/手/背与支撑面的接触、压缩和重心变化。

### `locomotion`

走、跑、跳、转身、上下楼、骑行等在空间中移动的动作。

- 默认整帧或连续动作序列生成。
- 必须有脚—地接触、步态相位、移动方向和环境透视。

### `handoff`

人物之间递交、接取、协作搬运、共同操作等多人共享对象的动作。

- 默认整帧生成。
- 必须说明当前承重者、共享接触阶段和最终归属。

### `environment-integrated`

人物被桌面、门、窗口、车辆、设备、前景或空间结构自然遮挡，或需要进入复杂空间。

- 必须整帧生成。
- 人物与环境共享透视、光源、接地和遮挡。

## 通用动作族门禁

### 推 / 拉

- 手掌或手指接触受力面。
- 身体重心向受力方向倾斜或反向抵抗。
- 对象出现位移、变形、开合或路径变化。

### 握 / 转

- 手指环绕把手、旋钮、工具或容器。
- 接触处有可信遮挡，不能在旁边捏空气。
- 对象角度、指针、齿轮或状态发生旋转响应。

### 按 / 点 / 滑

- 指尖与按钮或表面接触。
- 按钮有下压、颜色、位移或界面反馈。
- 滑动动作要有起点、路径和终点。

### 拿 / 举 / 搬 / 放

- 手臂、肩膀和重心体现重量。
- 物件不再由原支撑面承托，或明确落到新支撑面。
- 手与物件的抓握位置合理，物件不能漂浮。

### 插 / 拔 / 连接 / 组装

- 接口方向和尺寸合理。
- 显示部分插入、对齐或锁定关系。
- 结果状态显示连接完成、断开或模块归位。

### 写 / 画 / 签 / 擦

- 笔尖、刷头或擦除工具必须接触表面。
- 表面留下与运动路径一致的新增或消失痕迹。
- 手腕和视线朝向书写区域。

### 递 / 接 / 协作

- 递出者和接收者在同一物件上形成合理接触顺序。
- 共享阶段能看出承重转移。
- 结束时物件归属清楚。

### 开 / 关 / 揭示

- 手接触门把、盖子、抽屉、帘子或遮罩。
- 对象沿正确铰链、轨道或路径变化。
- 新出现或被隐藏的内容是动作结果。

### 坐 / 靠 / 扶 / 攀爬

- 身体与支撑面有真实接触和遮挡。
- 重心、关节角度和支撑方向匹配。
- 不允许身体漂浮、穿过桌椅或脚不着地。

### 走 / 跑 / 跳

- 至少一只脚与地面或台阶关系正确。
- 手臂摆动、躯干倾斜和移动方向一致。
- 背景透视、路径或尘点辅助表达位移，但不能替代正确步态。

### 看 / 指 / 思考 / 反应

- 视线、头部角度、手势和目标对象一致。
- 可使用透明人物叠加。
- 目标必须可见；指向空白不构成叙事动作。

## 构图泛化门禁

- 峰峰通常占画面面积8–18%或宽度12–20%；情绪特写可放大，动作解释图不得压住核心对象。
- 人物与目标对象、动作路径和结果状态共享一个清晰主方向。
- 关键接触点、动作对象和结果均位于内容安全区。
- 3/4身或全身优先；需要身体承重或移动时必须展示相关关节和支撑点。
- 不硬切关键肢体；不让字幕覆盖手、脚、工具或接触点。
- 有多步骤时，画面只表现当前一步，下一结果通过对象状态变化承接。

## 风格与空间融合

- 人物、对象和环境共享线条粗细、光源、阴影方向、透视、接地和景深。
- 峰峰保留全彩身份，轮廓可轻微手绘化，但脸、暖肤色、白hoodie双抽绳和深海军蓝夹克不能漂移。
- 深海军蓝主要属于人物；场景以白底黑线为主，软橙、浅蓝和绿色只表达动作或状态。
- 禁止白色矩形边、人物素材框、硬遮罩、透明白边和不同画风直接拼贴。
- 模型不生成生产级文字；标题、标签、数据和UI由本地代码叠加。

## 通用 Prompt 契约

生成操作型镜头时，Prompt必须写清：

```text
Actor: Feng
Intent: <为什么行动>
Action: <具体可见动词>
Target: <对象及其部位>
Contact points: <身体部位 ↔ 对象部位>
Motion/force: <方向、旋转轴、速度或视线>
Body response: <重心、躯干、关节、表情>
Object response: <位移、开合、亮起、痕迹、连接等>
Occlusion: <接触处谁遮挡谁>
Result state: <动作完成后的可验证画面>
```

避免“峰峰在操作设备”这类泛化描述；必须拆成可验证关系。

## 失败修复顺序

1. **动作读不出来**：把抽象动词改成身体部位、对象部位和结果状态。
2. **接触错位/悬空**：整帧重生成；不要移动PNG蒙混。
3. **没有受力感**：补重心、关节、运动方向和对象响应。
4. **人物与场景割裂**：整帧生成并统一线条、透视、光源和阴影。
5. **人物遮挡核心内容**：缩小至12–20%宽度，重排到目标侧面。
6. **身体漂浮或穿模**：补支撑点、接地阴影和前后遮挡。
7. **动作有了但结果不清楚**：增加对象状态变化，而不是增加更多装饰。
8. **文字乱码**：重生成无字底图，本地叠字。
9. **整体偏蓝**：运行 `feng-ip` 配色门禁，限制场景蓝并补暖色平衡。

## Hero Frame QA

逐项回答：

1. 谁在做什么，作用于什么？
2. 动作属于哪种 `interaction_mode`？
3. 身体或视线与目标的关系是否准确？
4. 若有接触，接触点和遮挡是否可信？
5. 身体重心、运动方向和对象响应是否一致？
6. 动作完成后出现了什么新状态？
7. 人物、对象和环境是否像同一张图？
8. 人物是否过大、硬切、漂浮或遮挡关键内容？
9. 移除峰峰后，动作因果链是否断裂？
10. 中文是否由本地代码层准确生成？

关键问题任一为“否”，不得进入批量渲染。
