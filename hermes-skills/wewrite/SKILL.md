# WeWrite · 微信公众号内容全流程助手（Hermes 本地适配版）

## Overview

This skill adapts the Obsidian note `20-Library/Skills/Content/wewrite_skill.md` into a local Hermes workflow. It covers the WeChat article pipeline:

```text
热点/选题 → 框架/素材 → 内容增强 → 写作 → HumanizerZH 去 AI 味 → SEO/自检 → 封面/正文配图 → professional-clean 排版 → 微信公众号草稿箱
```

It is now the shared cover-image, publisher, and formatter for dog-writing workflows. `dog-wechat-daily-writer` should call this skill for cover generation, article layout, and draft-box publishing instead of using a plain Markdown-to-HTML publisher.

## Main Script

Use:

```bash
python3 /root/.hermes/skills/productivity/wewrite/scripts/wewrite_publish.py \
  article.md cover.jpg \
  --account dog \
  --author '狗狗生活小百科' \
  --digest '给铲屎官的一份实用提醒'
```

Features:

- Loads `/root/.hermes/.env` automatically.
- Resolves account aliases from local config and environment.
- Generates covers through `scripts/image_gen.py` using ApiYi `gpt-image-2-vip` as the default and only enabled provider.
- Requires a HumanizerZH pass before publishing: remove AI-flavored phrasing, template transitions, over-polished slogans, excessive bold/emoji, vague attribution, and mechanical three-part structures while preserving facts and Markdown/image references.
- Applies WeChat HTML layout with inline CSS, theme-selectable via `--theme`.
- Supports Markdown body images (`![alt](local-path.png)`): uploads local body images through WeChat `media/uploadimg`, replaces them with WeChat-hosted URLs, and embeds them in article content.
- Uploads local cover as permanent thumb material.
- Publishes to WeChat draft API.
- Supports `--dry-run` to render HTML and verify account/token without creating a draft.
- Refuses missing credentials or mismatched dog account appid.

## professional-clean Layout

The renderer converts Markdown into WeChat-compatible HTML:

- H1 becomes title, not body content.
- Intro paragraphs get readable body styling.
- H2 sections use a left accent bar and warm clean typography.
- Body-image caption rule for writing workflows: Markdown image alt text is kept only for accessibility/context and should not be rendered as visible `figcaption`. Never publish visible labels such as `正文配图：主人观察...` below article illustrations; if a caption is ever explicitly required, it must be intentional article copy, not a generated/editor prefix.
- Lists become rounded checklist cards.
- Blockquotes become soft quote boxes.
- Paragraphs use `line-height: 1.85`, dark gray text, and mobile-friendly spacing.

## Common Pitfalls

1. **Using the old plain publisher.** For WeChat article drafts, use this WeWrite script so formatting matches the intended workflow.
2. **Duplicating drafts during tests.** Use `--dry-run` unless the user explicitly wants a real draft.
3. **Hardcoding AppSecret in notes.** Store secrets only in `.env`.
4. **Wrong account.** The dog alias resolves to `wx27855f8407f2c81c`; do not rely on defaults.
5. **Complex CSS.** WeChat strips some CSS. Use inline styles and simple tags.
6. **Body image alt text leaks as visible caption.** Old versions of `wewrite_publish.py` rendered Markdown image alt text as a visible `<figcaption>` below the image, showing text like "正文配图：主人观察..." in the draft. The current version strips both the figcaption AND the `正文配图：` prefix from the alt attribute. Future agents should not add any caption-like prefixes to Markdown image alt text in writing workflows.
7. **Vague ending instruction causes unrelated literary text in dog-writer.** The dog-writer skill's "结尾：温暖收束，引导收藏/转发" was too loose — the model would generate dog-themed poetic sentences unrelated to the article topic. The dog-writer skill now has a tightened ending rule (max 1 sentence, topic-only).
